## 题目

这是一场 60 分钟的一对一面试，面试官是用人经理（hiring manager），安排在技术轮之后。不需要提前提交材料，
但要带着准备好的内容来：一个与面试官所在团队对得上的“为什么是 OpenAI”的回答，你自己对 AGI 和 AI 安全的
看法，以及一组亲身经历的故事，覆盖你主动推动的项目、一次技术分歧、一次失败、一次顶住压力的经历、
一次与非工程背景伙伴的合作。问题分为五组。

### 动机

- 为什么是 OpenAI，而不是做同类问题的其他公司？
- 为什么是这个团队，为什么是这个具体的研究或产品方向，而不是同一家公司的另一个团队？
- 为什么是现在离开目前的工作——发生了什么变化？
- 过去每一次换工作，真正的原因是什么？

### 对 AGI 与安全的看法

- 你自己怎么看 AGI——一个系统要做到什么程度、在什么样的时间尺度上，你才会称它为 AGI？
- AI 安全对你来说具体意味着什么，落到你自己的工作上？
- 你怎么平衡快速迭代和验证质量 / 安全所需要的时间？

### 一道假设性的两难

- 你的上级要求你在没有做完本该做的安全测试的情况下上线一个模型功能，理由是不这样做会赶不上截止日期。
  你会怎么做？
- 同样的情况，只是截止日期来自外部合作伙伴的发布计划而不是内部目标，而且只是测试套件里的一部分会被
  跳过——这会改变你的做法吗？
- 同样的情况，只是提出要求的是另一个团队的平级同事，而不是你的上级，跳过的是对方负责的一项评审——
  这会改变你的做法吗？

### 过往经历

- 讲一个你从头到尾主动推动、并且交付上线的项目。
- 描述一次你和同事的技术分歧，以及它是怎么解决的。
- 你遇到过的最难的技术或协作问题是什么，你是怎么解决的？
- 讲一次你在乎的事情上失败的经历。
- 讲一次你顶住压力、或者对某个决定表达反对意见的经历，后来怎么样了？

### 跨职能合作

- 讲一个你和产品经理或其他非工程背景的伙伴紧密合作的项目。
- 讲一次你需要向非技术背景的同事说明一个技术取舍、好让对方能做决定的经历。
- 讲一次你和跨职能伙伴在范围或优先级上的分歧，以及它是怎么解决的。

面试前先向招聘联系人（recruiter）确认：这位用人经理来自哪个团队，是不是你入职后要加入的那个团队。
这决定了你带哪个版本的“为什么是 OpenAI”，以及“为什么是这个团队”这一问该答得多具体。

### 动机

这一组考察的是你的回答有没有和你自己的具体经历、这家公司的具体方向挂钩，而不是一句放到哪家公司都
成立的话。

“为什么是 OpenAI” / “为什么是这个团队”的骨架：把三样东西连起来——你自己的研究或工程方向、你对某条
产品线或某项公开研究工作的一个具体看法（不只是“我很欣赏它”）、以及这个岗位能让你做成什么在别处做不成
的事。提前准备两到三个版本——偏研究、偏安全、偏产品与基础设施——进面试前按面试官所在的团队选用对应的版本。
例如：你的研究或工程方向是 [方向 A]；你对 [某条产品线或某项公开研究工作] 的具体看法是 [你的实际判断，
不只是称赞]；这个岗位能让你做 [某类具体工作]，这是你在目前的岗位上做不到的。

“为什么现在离开” / 历次换工作原因的骨架：给每一份工作一句话，说清楚你当时在往哪个方向走——更大的问题
规模、不同的技术栈、更大的职责范围——而不是原来的地方哪里让你不满意。“为什么是现在”要落在一个具体的
变化上——项目已经交付、职责范围不再扩大——把它当作事实来讲，不要讲成抱怨。多次换工作的原因要能连成
一条一致的线，而不是每次一个说法、彼此矛盾。

最常见的失分方式：给一个放在任何一家 AI 公司都成立的空泛回答（“使命宏大”“AGI 很让人兴奋”）；不管
面试官是哪个团队都只准备一个版本；把过往的离职原因讲成对前公司或前上级的抱怨。对应做法：面试前读一遍
这家公司近期公开发布的产品、模型和安全方面的文章，从中挑一个你真有看法的点；再把面向这个团队的版本和
每一份工作的一句话原因写下来，而不是临场现编。

### 对 AGI 与安全的看法

这一组考察的是你有没有认真想过这些问题、能不能讲出具体的风险和具体的缓解办法，而不是看你站在哪一边。

骨架：先给出自己的工作定义（你说的“AGI”具体指什么、你说的“安全”具体指哪一类问题）→ 时间尺度给一个
区间，并说出它依赖的假设，而不是报一个年份 → 举一到两个你认为重要的具体风险（不是抽象的“失控”）→
说明这些风险和你自己的工作有什么关系、你会怎么去应对 → 坦率承认哪些地方自己还没想清楚。

关于“如何平衡快速迭代和质量 / 安全”，用一个你经历过的具体决策点举例——什么情况下你会主张放慢发布节奏，
什么信号会让你觉得可以按原计划上线——而不是抽象地说两者都重要。

最常见的失分方式：通篇只谈遥远的存在性风险、和自己的工作完全挂不上钩；或者反过来，只谈眼前的产品缺陷、
完全不涉及能力更强的系统带来的新风险；再或者整段回答没有一处“我还不确定”，显得像背好的立场而不是自己
的思考。

### 一道假设性的两难

这一组考察的是你会不会无条件照做、会不会没弄清约束就直接对抗，还是先把情况澄清、找一个同时照顾期限
和风险的办法，只有别无选择时才升级。

骨架：第一步，先问清楚事实——风险具体是什么、测试具体缺了哪一部分、期限到底是从哪里来的、能不能推迟
或者只满足一部分。第二步，提出一个同时照顾期限与风险的替代方案，并且和负责这些测试的人一起定，而不是
自己一个人说了算：缩小发布范围（只对内部或一小部分流量开放）；把测试拆成关键项和非关键项，先把关键项
跑完；或者带着加强的监控和快速回滚上线——最后这一种只适用于危害能很快被发现、并且可以撤回的风险。
第三步，如果对方仍然要求你越过自己认为不可接受的底线，通过正式渠道升级（找安全负责人、发起一次书面的
风险评审），并且告诉上级你正在这样做，把决定和理由留下书面记录，而不是默默照做，或者自己一个人把上线
拦下来。升级的目的，是让对这项风险负责的人在了解事实的情况下做决定，而不是让你赢下这场争论。这份记录
可以按这样的模板写：“已知风险是 [x]，缺失的测试是 [y]，提出的替代方案是 [z]；如果仍然要在没有完成 [y]
的情况下上线，需要 [该风险的责任人] 书面确认”。

两个变体用同一套骨架，变的只是要先澄清哪些事实。期限来自外部时：这个日期是不是真的不能动，合作伙伴
能不能接受缩小范围的发布；被跳过的那部分测试，覆盖的是不是这个功能真正带有的风险。提要求的是平级同事时：
负责执行这项评审的人，有没有权限决定免掉它；如果没有，就去问有这个权限的人，并且让自己的上级从你这里
知道这件事。先澄清、再提方案、最后才升级的顺序不变。

最常见的失分方式是走向两个极端：要么无条件服从（“上级决定了，我照做”），要么一上来就以安全的名义拒绝，
都不去了解风险和期限的具体情况。好的回答会先提出至少一个澄清事实的问题，再谈方案。

### 过往经历

这一组考察你本人具体做了什么、结果有没有可以核实的数字、事后有没有真的改变做法。

骨架：标准的 STAR——情境、任务、行动（用“我”而不是“我们”说明自己的部分）、结果（给一个数字或者可观察
的变化）。负面问题（失败、分歧、顶住压力）额外加一句：后来因为这件事，你改变了什么做法。

负面问题最常见的失分方式，是选一个无关痛痒的例子（“有一次我们对一个变量命名有分歧”），或者把失败归因
于别人的失误，而不是自己做的某个决定。要选一个真的付出过代价的故事——返工、错过时限、一个自己拍板但
结果不对的决定——行动部分把自己的角色讲清楚，结果给出数字。

| 故事 | 这个故事特有的失分方式 |
| --- | --- |
| 主动推动并交付 | 分不清是“我”还是“团队”做的，结果没有数字 |
| 技术分歧 | 只讲自己的立场，不讲对方的理由和最后是怎么达成一致的 |
| 最难的问题 | 把“难”等同于“耗时长”，说不出具体卡在哪个环节 |
| 失败 | 挑一个无关痛痒的例子，或者把责任推给别人 |
| 顶住压力 / 表达反对 | 只强调自己“是对的”，不说清楚当时的依据和后来怎么跟进的 |

### 跨职能合作

这一组考察你能不能和非工程背景的伙伴共事、把技术上的取舍翻译成对方能拿去做决定的语言。

骨架：说清楚具体的协作场景（和什么角色、做什么项目）、具体的分歧点或需要说明的取舍、你怎么把技术语言
翻译成对方关心的东西（时间、成本、用户体验，而不是实现细节）、以及最后的结果。讲范围或优先级上的分歧时，
还要用对方自己的说法讲出对方的约束，并说明最后是谁拍的板。例如：某个模型改动把推理延迟从 [X ms] 降到
[Y ms]，用的是 [某种方法]；让产品经理愿意优先排上这项改动的那句话，讲的是用户打开页面快了多少，
而不是这项技术本身。

最常见的失分方式是给一句没有例子支撑的空话（“我们沟通得很好”），或者复述技术细节而不是把它翻译成对方
能理解、能决策的信息。

### 面试官话不多的时候

如果面试官的提问很简短、对你的回答也不追问，不要因此被动地等下一个问题：每答完一段，主动补一句这段经历
和这个团队、这个方向的具体联系；同时提前准备两到三个自己真正想知道的问题——团队怎么定优先级、这个方向
接下来半年的重点是什么——在对话出现自然停顿的时候问出来。
