## 题目

这是一轮 60 分钟的口述“ML 设计”面试，面试官是搜索方向的专家。不需要在白板上画架构图：所有问题都围绕同一个系统背后的机器学习展开——文本向量模型怎么训练、检索怎么搭起来、结果怎么排序，以及怎么知道这些环节真的起作用。

待设计的系统：一个建立在内部知识库之上的文档问答产品，语料约 4000 万个段落（每段 200-400 个 token，已经切好块）。每天约有 500 万次查询，大致平分为两类：关键词式的短查询（2-5 个 token，像传统搜索框里输入的那种）和完整的自然语言问题。团队积累了一年的点击日志，规模与上述查询量相当（记录了查询、展示的排序列表、哪一条结果在哪个位置被点击），此外还有约 20,000 条人工评级的 `(query, passage, relevance grade 0-3)` 判定，标注供应商每个季度会再补充一批。检索加排序的延迟目标——端到端、不含下游的回答生成——中位数低于 150 毫秒，第 95 百分位低于 350 毫秒。

不在这一轮范围内的：接入与切块流水线、按文档的权限与多租户、回答生成与引用校验，以及任何硬件或容量估算。重点完全放在模型和检索算法上：怎样把一个查询变成一份排好序的段落列表。

按从训练到上线的顺序，回答下面的问题：

### (a) 训练向量模型

- 要用对比学习把一个预训练的文本编码器变成适合这个检索任务的向量模型。为什么这个训练目标适合这个任务？
- 精确地写出损失函数。每一项分别代表什么？温度通常取多大？
- 在还没有任何标注数据时，正样本对从哪里来？等到有了标注数据（比如自然语言推断式的句子对，或者问答对）之后，又从哪里来？
- 负样本要怎么选，每个锚点配多少个？
- batch size 在训练效果里起什么作用？把 batch size 翻倍，损失会怎么变？如果在批内负例之上再加挖掘出来的难负例，又会怎么变？

### (b) 检索流程

- 给定一个训练好的向量模型，把从一次原始查询到一份排好序的候选段落列表的路径走一遍。
- 为什么不直接用交叉编码器给语料里的每个段落和查询打分？双塔（bi-encoder）和交叉编码器（cross-encoder）在这里的分工是什么？
- 在这个规模下，你会用哪种索引去检索这些向量？它最主要的可调参数是什么？
- 有一半的查询量表现得像关键词搜索。单靠稠密检索够用吗？你会怎么把稠密检索和词法（稀疏）检索结合起来，两份分数量纲不同的排序列表又怎么合并？
- 什么是延迟交互（late interaction，以 ColBERT 为代表），它和双塔、交叉编码器分别有什么不同？代价是什么？

### (c) 排序

- 混合检索返回候选列表之后，单独的排序阶段能带来什么？为什么不能直接按检索分数排序？
- 排序模型（重排器）会用什么样的模型？它的训练数据和向量模型的训练数据有什么不同？
- 如果某个查询真正最好的段落根本没进入候选列表，重排器能把它救回来吗？由此看，精力应该怎样在检索阶段和重排器之间分配？
- 重排器要打分的候选列表大小怎么定？这个选择要权衡什么？

### (d) 评测与迭代

- 检索阶段和最终排序列表分别会报告什么离线指标？为什么不一样？结合 recall@k、MRR、nDCG 来回答。
- 有了前面说的人工标注和点击日志，你会怎么为这个产品搭建一份评测查询集？
- 上线之后，除了离线指标，你还会跟踪哪些线上信号？
- 上线几个月后，你要怎么发现检索质量在悄悄变差？

动手回答之前值得先确认：这里的“标注数据”指的是句子对标签（蕴含/矛盾），还是查询-段落的相关性判定——两者喂给模型的方式不一样。下面的解答两种都覆盖。

### (a) 训练向量模型

训练目标是对比式的：把查询的向量拉向能回答它的段落，推离不能回答它的段落。线上正是按查询与段落向量的相似度来排序，所以这个目标训练的就是最近邻搜索用来排序的那个量，而不是先训练一个分类器、再回头比较它的向量。

损失函数用 InfoNCE。对一个锚点（这里是查询）$q$、它的正样本段落 $p^+$，以及 $N$ 个负样本段落 $\lbrace p_1^-, \dots, p_N^- \rbrace$：

$$L_{\text{InfoNCE}} = -\log \frac{\exp(\mathrm{sim}(q, p^+) / \tau)}{\exp(\mathrm{sim}(q, p^+) / \tau) + \sum_{i=1}^{N} \exp(\mathrm{sim}(q, p_i^-) / \tau)}$$

`sim(·,·)` 是 L2 归一化向量之间的余弦相似度，取值在 $[-1, 1]$ 之内，所以 softmax 的尺度完全由温度 $\tau$ 决定。分母把正样本和每一个负样本都加了进去，因此这个损失恰好是在 `sim / τ` 上做的 $(N+1)$ 类交叉熵，正确类别就是正样本。

批内负例（in-batch negatives）几乎不花额外代价：每个锚点的正样本本来就要编码，所以 batch size 为 $B$ 时，同一批里另外 $B-1$ 个正样本可以直接当负样本用，不需要多跑一次编码器，只多算一个 $B \times B$ 的相似度矩阵。于是每个锚点有 $N = B - 1$ 个负样本，$B$ 取显存允许的最大值（几百到几千），再加上少量挖掘出来的难负例：DPR 给每个问题配一个，而且每个锚点不只和自己的难负例对比，还和同一批里其他问题的难负例对比。

把 batch size 翻倍，变的只是分母里的求和：$N$ 从 $B-1$ 变成 $2B-1$，正样本项不变。损失的数值本身会变大——一个完全分不清各个候选的模型，损失是 $\log(N+1) = \log B$，$B$ 翻倍就多出 $\log 2$——所以不同 batch size 下的损失值不能直接比较。效果变好的原因是：批内求和是对“在整个语料上做 softmax”的一次采样近似，样本越多近似得越好，也越有可能碰巧包含一个难负例。挖掘出来的难负例加进的是同一个求和，只是它们是按高相似度特意挑出来的，不是随机的；softmax 按相似度给每个负样本加权，所以这样一项就可能占去负样本一侧的大部分梯度，少量难负例每一步带来的训练信号比大量容易的负例还多。

损失对某个负样本相似度的梯度，等于它的 softmax 概率除以 $\tau$，所以两个负样本的梯度相差 $\exp(\Delta\mathrm{sim} / \tau)$ 倍。举个例子：正样本的余弦相似度是 0.75，四个负样本分别是 0.68、0.40、0.10 和 -0.10。$\tau = 0.07$ 时，0.68 这一个负样本就占了负样本一侧 98.2% 的概率质量，它的梯度约是最容易那个负样本的 69,000 倍；$\tau = 0.20$ 时这个占比是 75.7%，$\tau = 0.02$ 时接近 100%。温度过低，梯度几乎只盯着最接近的那一个负样本，一旦它恰好是假负例（false negative，实际相关、却被标成负样本的段落），训练就会对这一个错误非常敏感；温度过高，所有负样本的权重几乎相同，最需要被分开的那些“差一点就对”的段落，得到的推力并不比毫不相关的段落大多少。固定的温度一般取 0.01 到 0.1（SimCSE 用 0.05）；也可以像 CLIP 那样把 $\tau$ 当作可学习的参数。

没有标签时，正样本对用 SimCSE 的做法构造：把同一段文本送进编码器两次；dropout 在每次前向传播时都是随机的，同样的输入会得到两个略有不同的向量，这一对就当作正样本——这种数据增强不会像改写那样改变原意。有 NLI 式的句子对标签时，有监督的 SimCSE 把每个前提的蕴含（entailment）假设作为正样本，把针对同一个前提写的矛盾（contradiction）假设作为难负例——它们在话题和用词上都和锚点很接近、意思却是错的，随机的批内文本很少能提供这种信号；中立（neutral）假设不用。有问答数据时，正样本对是（问题，包含答案的段落），DPR 用 BM25 检索这个问题，把排在前面、与问题用词重合却不包含答案的段落当作难负例。在这个产品里，点击日志是这类样本对最大的来源：被点击的段落是该查询的正样本，排在它前面、展示了却没被点的段落可以作为难负例的候选。

假负例在挖掘出来的负例和批内负例里都会出现——语料里另有一份重复的段落，或者另一篇文档同样能回答这个问题——拿它当负样本训练，会把一个正确答案从查询身边推开。缓解办法：丢掉得分与标注正样本接近得不合情理的挖掘候选；同一批里近乎重复的段落先去重；有了重排器之后，凡是重排器也打高分的挖掘负例一律丢弃。

### (b) 检索流程

整条路径是：用双塔模型把查询编码一次；从近似最近邻索引里取出前几百个段落，同时在同一批段落上并行跑 BM25；按名次把两份列表融合；把前 K 个（候选列表）交给重排器。

双塔模型把查询和段落分别独立编码，所以每个段落的向量只需要离线算一次。交叉编码器把查询和段落拼在一起、联合过一遍模型，每一层都能跨两者做注意力——精度更高，但什么都没法预先算好，给整个语料打分意味着每个查询要做 $4 \times 10^7$ 次前向传播。分工由此而来：双塔负责在整个语料上保证召回，交叉编码器负责在候选列表上保证精度。

精确搜索对每个查询都要扫过全部 $4 \times 10^7$ 个向量；近似索引只访问其中很小的一部分，代价是一点可以调节的召回损失。标准的选择有两类：IVF（把向量划分成粗粒度的簇，只搜索最近的几个簇），通常再配上乘积量化（product quantization）；以及 HNSW 这样的图索引（每个向量是一个节点，与邻近的向量连边，检索时沿着边走向查询）。这里 HNSW 是更合适的默认选择：召回/延迟曲线好，段落持续新增时也不需要重新训练簇中心；代价是每个向量占的内存（图上的边加上接近全精度的向量）比 IVF+PQ 的压缩编码大。最主要的可调参数是搜索的广度——HNSW 的 `efSearch`（候选队列的大小），IVF 里对应的是 `nprobe`（探查的簇数）：它在查询时用延迟换召回，不需要重建索引，取值靠在一批抽样查询上对照精确搜索测出的召回率来定。

稠密检索能跨越改写泛化，但对精确的 token 比较弱——缩写、版本号、关键词式查询里直接点名的某个标识符；稀疏的词法检索（BM25）正好相反。这里一半的查询量表现得像关键词搜索，单靠稠密检索不够：对每个查询两种检索都跑、再合并两份列表，才能同时补上两边的短板。

两份分数的量纲不同——余弦相似度有界，BM25 的分数无界，还依赖长度——所以倒数排名融合（reciprocal rank fusion）只用名次，不用分数：

$$\text{score}(x) = \sum_{r \in \lbrace \text{dense}, \text{sparse} \rbrace} \frac{1}{k_0 + \text{rank}_r(x)}$$

其中名次 1 最好，没有出现在某份列表里的段落在那一份上贡献为零。常数 $k_0$（原论文取 60）的作用是把每份列表的头部压平，让“两边都认可”胜过“某一边的第一名”：在两份列表里都排第 10 的段落得分是 $2/70$，高于只在一份列表里排第 1 的 $1/61$；而 $k_0 = 0$ 时前者只有 0.2，会输给后者的 1。另一种做法是把两份分数按查询各自归一化后加权求和，它保留了真实的分差，调得好时效果可以更好，但只要查询构成或任何一个检索器变了，权重就得重调，所以默认用倒数排名融合。

延迟交互以 ColBERT 为代表：不再把每段文本池化成一个向量，而是给查询和段落的每个 token 各留一个向量，用 MaxSim 给一对（查询，段落）打分——对查询里的每个 token，取它和段落各 token 的最大相似度，再求和：

$$\text{score}(q, p) = \sum_{i} \max_{j} \; u_i \cdot v_j$$

其中 $u_i$ 是查询各 token 的向量，$v_j$ 是段落各 token 的向量，都做了归一化，点积就是余弦相似度。和交叉编码器不同，段落一侧的 token 向量仍然可以离线算好；和双塔不同，查询的每个 token 都能匹配到段落里与它最贴合的那个 token，抓住被单个池化向量平均掉的短语或实体。代价一是存储——这里每个段落约 300 个向量，总共约 $1.2 \times 10^{10}$ 个，而不是 $4 \times 10^7$ 个，所以 ColBERT 把每个 token 的向量维度取得很小（128），ColBERTv2 又进一步压缩了 token 向量——二是检索要分两步：先对查询的每个 token 在全部 token 向量上做一次最近邻查找，汇集出候选段落，再在每个候选的全部 token 上精确计算 MaxSim。只有细粒度的短语匹配确实重要时，才值得为它搭这一套基础设施；它不是双塔的默认替代品。

### (c) 排序

检索阶段的分数来自便宜到能跑遍整个语料的模型，因此比同时读查询和段落的模型粗糙；重排就是把这个更贵的模型只用在候选列表上，在这个规模下才负担得起。

重排器是一个交叉编码器，按逐点（pointwise）方式打分——每个（查询，候选）对独立跑一次前向传播，可以批处理，开销随候选数线性增长；代价是逐点打分看不到候选之间的冗余，而把整份候选列表放在一起一次打分的做法可以发现并惩罚冗余。150 毫秒的中位数预算可以这样分：查询编码约 10 毫秒，两路检索并行再加融合约 30 毫秒，网络开销约 10 毫秒，留给重排器的最多 90 毫秒——在 GPU 上用一个小的交叉编码器，大约能给 100 个量级的候选打分，这个数要实测，不能想当然；第 95 百分位的 350 毫秒用来吸收排队和个别慢的索引分片。

它的训练数据和向量模型不一样：向量模型只见过“一个正样本对一批负样本”，没有“好多少”的概念；重排器则在分级的标签上训练——没有留作评测的那部分人工判定，以及经过位置偏差（position bias）校正的点击日志：排在第 5 位的点击比排在第 1 位的点击更能说明相关，因为看到那么靠后的用户少得多，所以原始点击率要先除以每个位置被看到的概率的估计值，才能当作相关性标签。

重排器只能给拿到手的候选重新排序：最好的段落如果没有进入候选列表，怎么重排也救不回来。它的上限就是检索阶段在候选规模 K 上的 recall@K，所以混合检索和一个足够大的 K，比继续打磨一个已经够准的重排器更重要，候选列表上的 recall@K 也要和重排器自己的指标分开跟踪。

K 的取值看评测集上 recall@K 随 K 变化的曲线：取曲线变平的那个点，上限由重排器的延迟（大致随 K 线性增长）决定。K 太小，相关段落根本到不了重排器；K 太大，延迟花在了不再带来召回的候选上。

### (d) 评测与迭代

检索阶段和最终列表的评判方式不同。recall@k——一个查询的相关段落里有多大比例出现在前 k 个，再对查询取平均——适合检索阶段，因为它不看前 k 个内部的顺序，而重排器反正会把候选列表重新排一遍。MRR（第一个相关结果的名次的倒数，对查询取平均）和 nDCG@k 对顺序敏感，衡量的是真正展示给用户的那份列表，因为最好的结果落在第几位就是用户的实际体验。nDCG 用的是第 $i$ 位结果的 0-3 分级 $g_i$，而不是二元标签，常用的是指数增益的形式 $\text{DCG@}k = \sum_{i=1}^{k} (2^{g_i} - 1) / \log_2(i + 1)$，再除以最优排序的 DCG，使完美的列表得 1 分。

约 20,000 条人工判定是规模小但无偏的锚点。按查询来切分：固定的一部分查询（关键词式和自然语言式都要覆盖到）作为冻结的评测集，不进入任何训练或难负例挖掘的流水线，每次模型或索引有变化都重新跑一遍；其余的可以用来训练重排器。点击日志提供规模大得多、但噪声也更大的第二份评测集：查询从真实流量里抽样，标签来自经过上述位置偏差校正的点击，而每个位置被看到的概率，要从一小部分随机打乱顺序展示的流量里估计。

线上值得跟踪的信号有：首位结果的点击率、同一会话内的改写率（用户紧接着又发了一个相关查询，说明第一次的结果没有解决问题），以及零结果率和无点击率。这些信号都不能证明被点击的段落真的回答了问题，只能说明它看起来有希望，所以它们是离线判定的补充，不能替代。

汇总指标会掩盖问题：某个细分上的退化可能被另一个细分上的提升抵消，所以指标要按查询类型和语料区域分开跟踪。冻结的评测集每晚对着线上的索引和模型重跑一遍，而不只是在发布时跑，这样就能在问题变成线上信号的缓慢漂移之前，发现那些并非由模型改动引起的退化，比如一次索引重建悄悄丢了一个分片。冻结的评测集看不到查询本身的变化，所以每个季度的标注批次都从近期流量里重新抽样查询：如果这批新查询上的指标与冻结集上的指标差距越拉越大，就说明发生了漂移。

### 追问

- Triplet loss，即带固定间隔 $m$ 的 $\max(0, m + \mathrm{sim}(q, p^-) - \mathrm{sim}(q, p^+))$，一次只看一个负样本：只要违反了间隔，它对两个相似度的梯度就是常数 $\pm 1$，否则为零，而且每个三元组都不理会批里的其他候选。InfoNCE 的 softmax 则让批里每个负样本都得到一个随其相似度增大的梯度。
- 把交叉编码器的分数蒸馏进双塔——用重排器当老师，把它的分数当软标签，构造额外的训练对——能在不增加线上延迟的前提下让检索本身更准。
- 梯度累积代替不了更大的 batch：负样本只来自同一次前向传播里一起编码的样本，每个 micro-batch 仍然只和自己那几个样本对比。在计算损失之前把各张卡上的向量汇集到一起，才能真正扩大负样本池。

```python
import math

import torch
import torch.nn.functional as F

torch.manual_seed(0)

# One anchor's similarities to its positive (index 0) and four negatives, ordered from a close,
# hard negative down to an easy, unrelated one.
sims = torch.tensor([0.75, 0.68, 0.40, 0.10, -0.10], requires_grad=True)
tau = 0.07
target = torch.tensor([0])

logits = sims / tau
loss = -F.log_softmax(logits, dim=0)[0]
loss_xent = F.cross_entropy(logits.unsqueeze(0), target)
assert torch.allclose(loss, loss_xent, atol=1e-6)          # InfoNCE == (N+1)-way cross-entropy

loss.backward()
with torch.no_grad():
    probs = F.softmax(logits, dim=0)
    onehot = torch.zeros_like(probs)
    onehot[0] = 1.0
    grad_formula = (probs - onehot) / tau
assert torch.allclose(sims.grad, grad_formula, atol=1e-6)  # d(loss)/d(sim_j) = (softmax_j - onehot_j) / tau

neg_grad = sims.grad[1:]
assert neg_grad[0] > neg_grad[1] > neg_grad[2] > neg_grad[3] > 0   # hardest negative gets the largest gradient
ratio = (neg_grad[0] / neg_grad[3]).item()
assert math.isclose(ratio, math.exp((0.68 - (-0.10)) / tau), rel_tol=1e-3)   # exp(delta_sim / tau)
print(f"loss = {loss.item():.4f}, p(positive) = {probs[0].item():.4f}, p(hard negative) = {probs[1].item():.4f}")
print(f"hardest/easiest negative gradient ratio = {ratio:,.0f}x")

# temperature sweep: share of the total negative softmax mass carried by the hardest negative
shares = {}
for t in (0.20, 0.07, 0.02):
    p = F.softmax(sims.detach() / t, dim=0)[1:]
    shares[t] = (p[0] / p.sum()).item()
    print(f"tau={t:.2f}: hardest negative carries {shares[t]:.1%} of the negative-side softmax mass")
assert shares[0.02] > shares[0.07] > shares[0.20]           # lower temperature concentrates the gradient further

# a model that cannot tell the candidates apart scores log(N + 1) = log B; doubling B adds log 2
flat = {B: F.cross_entropy(torch.zeros(1, B) / tau, target).item() for B in (128, 256)}
assert math.isclose(flat[128], math.log(128), rel_tol=1e-5)
assert math.isclose(flat[256] - flat[128], math.log(2), rel_tol=1e-4)


# triplet loss: the gradient w.r.t. (sim_pos, sim_neg) is (-1, +1) while the margin is violated, else 0
def triplet_grad(sim_pos, sim_neg, m=0.2):
    s = torch.tensor([sim_pos, sim_neg], requires_grad=True)
    torch.clamp(m + s[1] - s[0], min=0).backward()
    return tuple(s.grad.tolist())


assert triplet_grad(0.75, 0.74) == triplet_grad(0.30, 0.74) == (-1.0, 1.0)
assert triplet_grad(0.75, 0.10) == (0.0, 0.0)


# reciprocal rank fusion: with k0 = 60, 10th place in both lists beats 1st place in only one
def rrf(ranks, k0):
    return sum(1 / (k0 + r) for r in ranks)


assert math.isclose(rrf([10, 10], 60), 2 / 70) and math.isclose(rrf([1], 60), 1 / 61)
assert rrf([10, 10], 60) > rrf([1], 60)
assert math.isclose(rrf([10, 10], 0), 0.2) and rrf([10, 10], 0) < rrf([1], 0) == 1.0

# late interaction keeps one vector per token: 40M passages of about 300 tokens
assert 40_000_000 * 300 == 1.2e10

# median latency budget in ms: query encoding, parallel retrieval + fusion, network, reranker
assert 10 + 30 + 10 + 90 <= 150
```
